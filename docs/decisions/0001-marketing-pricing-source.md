# 1. Where the marketing site gets its prices

Date: 2026-08-23
Status: **Accepted** (live wiring: **Deferred**, not rejected)

## Context

The site quoted `$299` for a tier that sells at `$549`, and `$79` for one that
sells at `$59`, for months. Nobody edited those files. The catalogue moved and
the copy did not follow.

The original plan was to fix this by reading prices live from
`/billing/packages` instead of `/marketing/plans`, on the argument that the
package endpoint carries both currencies, already includes Growth, and picks up
a new package with no deploy.

That argument turned out to be half right. `/billing/packages` serves
`id, key, name, description, sortOrder, badge` plus four price fields, and
nothing else. Its `features` array is empty for every package, Growth's
`description` is `null`, and every `badge` is `null`. It solves prices. It does
not solve feature copy.

## Decision

### 1. Live wiring is deferred

Prices are the **stable** half of the pricing page; features are the
**volatile** half. Prices change a handful of times a year. The feature matrix
changes with every tier decision. Wiring the stable half live buys little and
costs a runtime dependency, an error path, an anonymous-currency decision, a
CORS surface and a stale-cache window.

Two further points weighed against it:

- The site **already** fetches prices live, from `/marketing/plans`. Live
  wiring would not be new capability, only a change of endpoint.
- The wrong annual figures on the page today come *from* that live fetch ,
  generated by `ANNUAL_DISCOUNT = 0.8` in `marketingPlansService`. Live data
  moved the error out of a file you can grep and into a constant in another
  repo.

Deferred, not rejected. Revisit when **either** of these becomes true:

- packages start being added or repriced often enough that a deploy per change
  is a real constraint; or
- the plan/package split is unified, so reading the package side stops meaning
  "depend on a second, divergent source of truth".

### 2. Feature copy stays in this repo

Three options were considered for serving marketing feature copy:

| Option | Verdict |
| --- | --- |
| A. Copy map in the backend, keyed by capability | Least likely to drift on **tier assignment**: move a capability and the bullets follow. Costs a backend deploy for a copy change, which is the pressure that pushes people to edit the DB, where `ensureSeeded()` reverts it on the next boot. |
| B. A `marketing_features` table | Rejected. A second authoring surface with no compile-time link to the capability enum, no diff, no review, no rollback, and the same seeding trap as `plan_catalog`. |
| C. Bullets stay in this repo | **Chosen.** Drifts on wording, but visibly, in a reviewable PR, and assertably. |

Option A is the right answer *when it is needed*. It is not needed now.

The thing that prevents drift is not where the string lives. It is whether the
include/exclude booleans are checked against the entitlement table.

### 3. A drift check instead

`scripts/check-price-drift.mts`, run in CI by `.github/workflows/price-drift.yml`.

It compares the live `/billing/packages` catalogue against **both** this repo's
price map **and** `/marketing/plans` (what the cards actually render), per tier,
per currency, per interval, plus the tier set itself.

Two sources are checked because the repo sheet is only the fallback. Checking it
alone would report "all clear" while the live page showed a different set of
tiers at different prices, which is precisely the state the site is in today.

## Consequences

- A price edited by hand into a value the catalogue does not sell fails the PR.
- A package added to the catalogue with no card on the site fails the schedule.
- A retired tier lingering on the site fails the same way.
- Feature *wording* is still unchecked. That is a known, accepted gap; the
  `featureCategories` matrix is the place to close it next, by asserting its
  booleans against the backend entitlement config.

## What this did not fix

Both live in the Backend and are recorded as expiring waivers in the check:

1. `ANNUAL_DISCOUNT = 0.8` in `marketingPlansService` generates the annual
   figures the cards show, under-quoting the real ten-month rate by ~4%.
2. `plan_catalog.GROWTH.show_on_marketing_site = false`, so there is a Growth
   column in the comparison matrix with no Growth card above it.
